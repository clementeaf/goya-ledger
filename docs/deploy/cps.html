1. Introduction

1.1 Overview

This Certificate Practice Statement (CPS) describes the practices and procedures employed by Goya Ledger OÜ ("Goya", "we") operating as a Trust Service Provider (TSP) under Regulation (EU) No 910/2014 (eIDAS). Goya provides advanced electronic signature services, time-stamping, and verifiable credential issuance.

1.3 PKI participants

  • Certification Authority (CA): Goya Ledger root CA (offline) and intermediate CA (operational). Two-tier hierarchy per ETSI EN 319 411-1.
  • Registration Authority (RA): Identity proofing via external identity verification providers. Supports Chilean RUT (Ley 19.799), UAE Emirates ID, and EU national eID schemes.
  • Subscribers: Natural and legal persons requesting certificates or verifiable credentials.
  • Relying Parties: Entities that verify signatures, timestamps, or credentials issued by Goya.

1.4 Certificate usage

Certificates and credentials issued by Goya are intended for:

  • Advanced electronic signatures (eIDAS Art. 26) using ML-DSA-65 or ECDSA P-256
  • Electronic seals for legal persons
  • Authentication in the EUDI Wallet ecosystem (OID4VCI/OID4VP)
  • Document notarization and proof of existence

3. Identification and authentication

3.1 Naming

Subscriber identifiers use the Decentralized Identifier (DID) scheme: did:goya:{pubkey_hex[..16]}. DIDs are derived deterministically from the subscriber's public key.

3.2 Initial identity validation

Before issuing an advanced electronic signature certificate, Goya verifies the subscriber's identity through:

  • Remote automated verification: Integration with external identity verification providers (eID schemes, video-ident services) via the IdentityVerificationProvider interface
  • Document validation: National ID format and check digit verification (RUT mod-11, Emirates ID Luhn, EU national ID)
  • eIDAS Level of Assurance: In-person = High, Video conference = Substantial, Remote automated = Substantial (when using certified eID), Low otherwise

3.3 Identification and authentication for re-key

Re-keying requires the subscriber to authenticate using their existing DID and demonstrate control of the current private key, or repeat the initial identity verification process.

4. Certificate life-cycle operational requirements

4.1 Certificate application

Subscribers request certificates via POST /api/v1/ra/proof with identity evidence. The RA validates the evidence and, upon approval, issues a certificate signed by the intermediate CA.

4.2 Certificate issuance

Certificates are issued after successful identity proofing. The process:

  • RA verifies identity via external provider or manual review
  • CA signs certificate with configurable algorithm (ECDSA P-256 or ML-DSA-65)
  • Certificate published to subscriber and registered in certificate store
  • Audit event emitted (AuditAction::CertificateIssued)

4.3 Certificate revocation

  • Subscribers may request revocation at any time via POST /api/v1/msp/revoke
  • Goya revokes certificates upon: subscriber request, suspected key compromise, cessation of operations, or inaccurate information
  • CRL updated within 1 hour of revocation
  • OCSP reflects revocation immediately
  • Audit event emitted (AuditAction::CertificateRevoked)

4.4 Certificate renewal and re-key

Certificate renewal follows the same identity verification as initial issuance. Re-key generates a new key pair; the old certificate is revoked.

5. Facility, management, and operational controls

5.1 Physical security

Production infrastructure operates on Fly.io with geographic distribution per the Business Continuity plan (GOYA-BCDR-001). Root CA key material is generated and stored offline.

5.2 Procedural controls

  • Dual control for root CA operations (key ceremony)
  • Separation of duties between RA and CA functions
  • All administrative actions logged to tamper-evident audit trail

5.3 Personnel controls

Personnel with access to CA systems undergo background checks and security awareness training per NIS2 Art. 21(2)(g).

6.2 Private key protection

  • Private keys generated using OS CSPRNG (OsRng)
  • Keys encrypted at rest with Argon2id + AES-256-GCM
  • Key zeroization on provider drop (implemented in SigningProvider)
  • HSM abstraction available (HsmConfig) for production deployments

6.3 Cryptographic algorithm lifecycle

Algorithm deprecation managed via AlgorithmPolicy with configurable deadlines. Archived contracts re-signed before algorithm rejection via preserve_expiring() sweep.

6.4 Time-stamping

RFC 3161 Time Stamp Authority with NTP-synchronized clock. Drift guard rejects timestamps when clock offset exceeds 5 seconds. DER-encoded timestamp tokens available at /api/v1/tsa/timestamp/der.

7. Certificate and CRL profiles

7.1 Certificate profile

X.509 v3 certificates per RFC 5280. Subject contains subscriber DID. Key usage and extended key usage set per certificate purpose.

7.2 CRL profile

X.509 v2 CRL per RFC 5280 §5. Available in DER at /api/v1/crl/der and PEM at /api/v1/crl/pem.

8. Compliance audit and other assessments

Goya commits to:

  • Annual internal security review per ETSI EN 319 401 §7.9
  • Conformity assessment by accredited CAB when seeking qualified status
  • Vulnerability disclosure per CRA (EU 2024/2847) via /.well-known/security.txt
  • Incident notification per NIS2 Art. 23 (24h early warning, 72h full report)
